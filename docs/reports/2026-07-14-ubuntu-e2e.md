# Ubuntu 24.04 end-to-end verification — 2026-07-14

## Итог

**PASS в проверенной локальной границе Ubuntu 24.04 x86_64; public VPS/DNS/ACME/webhook — BLOCKED.** На чистой persistent QEMU VM подтверждены установка и безопасный повторный запуск, восстановление после reboot, только ожидаемые product TCP ports, недоступность PostgreSQL снаружи, локальный HTTPS без отключения проверки сертификата, повторяемый импорт 18 workflow, backup/restore и approved update/rollback с exact data assertions.

## Воспроизведённый путь

1. Создана новая QEMU VM из официального Ubuntu 24.04 cloud image с architecture `x86_64` и persistent disk.
2. Установлены exact Docker Engine/Compose packages, затем выполнен installer dry-run. Dry-run не создал `.env` и не изменил Docker runtime.
3. Выполнена чистая non-interactive установка с `N8N_HOST=n8n.localhost`, затем безопасный rerun с тем же config.
4. VM остановлена и запущена заново через Lima. Boot ID изменился, а Compose services и persistent data восстановились автоматически.
5. Проверены listeners, internal health, закрытые `5432`/`5678` и локальный TLS с явным trust к Caddy local CA.
6. Production `scripts/import-workflows.sh` выполнен дважды. SQL-сравнение с catalog подтвердило 18 IDs, отсутствие duplicates и inactive state.
7. После удаления исходного app stack запущен guard-railed destructive rehearsal с marker `T-0012-DISPOSABLE`: backup, полное удаление database, restore, update, rollback, data-preserving uninstall/restart и tampered archive.

Команда destructive части требует отдельный temporary root и marker до первого обращения к Docker:

```bash
work_root="$(mktemp -d /tmp/t0031-lifecycle.XXXXXX)"
printf 'T-0012-DISPOSABLE\n' > "$work_root/.t0012-disposable"
sudo ./tests/destructive_lifecycle_rehearsal.sh \
  --work-root "$work_root" \
  --confirm-disposable T-0012-DISPOSABLE
```

## Обнаруженные и исправленные дефекты

Реальный fresh install выявил четыре проблемы installer:

- отсутствие firewall opt-in возвращало status `1` под `set -e`;
- допустимый doctor result `WARN` попадал в `ERR` trap до обработки exit code;
- `compose ps -q | grep -q` под `pipefail` мог завершиться ошибкой SIGPIPE при нескольких services;
- runtime config принимал произвольный `N8N_VERSION`, хотя Compose pin установлен на `2.29.10`.

Installer теперь явно принимает только exact pin `2.29.10`, безопасно обрабатывает doctor `WARN`, проверяет полный список running IDs и возвращает success при выключенном firewall opt-in. Удалены также не переносимые escape-последовательности awk, которые давали warning на Ubuntu `mawk`.

## Оговорки и отклонённые попытки

- Первый app root находился в `/tmp`; reboot очистил bind-mounted Caddy config. Результат отклонён как ошибка размещения test harness. Канонический прогон повторён из persistent guest home.
- macOS tar transfer создал AppleDouble `._*` только в guest copy; файлы удалены до импорта и никогда не находились в Git.
- Полный `tests/workflow_catalog_test.sh` прошёл static/schema/safety/import этапы, но stdout `n8n export:workflow --all` оказался усечён под QEMU, и JSON parse завершился ошибкой. Поэтому весь gate не объявлен PASS; task-specific evidence основан на успешном production importer и прямом SQL-сравнении catalog IDs/state.
- Host Lima не смог пробросить guest `80/443` на macOS, потому что эти host ports уже были заняты. Проверка выполнена внутри guest с реальными wildcard listeners и TLS; публичная доступность не заявляется.

## Redaction и оставшийся внешний gate

В Git не добавлены `.env`, raw logs, backup archives, credentials или decrypted secrets. Synthetic credential расшифровывался только внутри disposable container для сравнения и удалялся. Сохраняемый manifest прошёл checksum verification и secret scan; failure log содержит только ожидаемый checksum mismatch.

Для снятия `BLOCKED` нужен отдельный disposable Ubuntu 24.04 x86_64 VPS, управляемый public IPv4 и домен. На нём следует повторить installer и reboot, затем проверить внешний DNS A-record, ACME chain, HTTPS editor, test webhook callback и внешний отказ TCP `5432`. До такого прогона этот отчёт нельзя использовать как evidence публичного deployment.
