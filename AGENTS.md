# AGENTS.md

## Область действия

Правила действуют для всего репозитория `n8n Entrepreneur Starter Kit`.

## Источник истины

- Projects Control (`projects-control-work`) — источник истины для эпиков, задач, зависимостей, leases, документов, evidence и review.
- `docs/product-brief.md` и `docs/architecture.md` — канонические продуктовые и архитектурные документы.
- ADR фиксируют решения. Изменение принятого решения требует нового ADR или явного supersede существующего.

## Обязательный lifecycle

1. Найти dependency-ready задачу в Projects Control.
2. Запустить идентифицированный agent run.
3. Прочитать `task_context`, зависимости и связанные документы.
4. Выполнить `document_check`; stale или missing документы нельзя использовать как основание работы.
5. Взять задачу через `task_claim` до изменения файлов.
6. Работать только в scope задачи; для долгой работы продлевать lease.
7. Запустить проверки, зарегистрировать изменённые документы, добавить evidence.
8. Отправить задачу на review. Реализатор не одобряет собственную работу.
9. Независимый reviewer проверяет evidence и реальные изменения и выносит решение.

## Approval gate

Владелец одобрил backlog 2026-07-13. Foundation-only gate снят, но dependency и architecture gates Projects Control остаются обязательными: runtime implementation нельзя начинать до завершения `T-0002`, `T-0003` и `T-0004`.

До завершения `T-0004` запрещено:

- создавать Docker Compose stack и runtime-конфигурацию;
- реализовывать любые shell-скрипты;
- создавать workflow JSON и fixtures;
- подключать или вызывать внешние credentials;
- запускать продуктовые контейнеры, VPS или deployment;
- создавать CI/CD продуктовой реализации.

## Инженерные правила после снятия gate

- Поддерживать только Ubuntu 24.04 LTS x86_64, пока отдельная задача не расширит матрицу.
- Использовать официальный n8n image и явно закреплённые версии; тег `latest` запрещён.
- Не хранить секреты, credentials, access tokens и реальные персональные данные в Git, workflow JSON, fixtures или logs.
- `.env` создаётся локально с правами `0600`; постоянный `N8N_ENCRYPTION_KEY` обязателен.
- PostgreSQL не публикуется наружу; Docker socket не монтируется в n8n; лишние privileges запрещены.
- Опасные бизнес-действия по умолчанию требуют human approval; draft-only включён по умолчанию там, где применимо.
- Скрипты должны иметь `--help`, безопасную обработку ошибок, понятные русские сообщения и не выводить секреты.
- Фактические проверки отделяются от предположений. Нельзя заявлять об успешном VPS, backup/restore, HTTPS или provider test без evidence.
- Документация для пользователя пишется по-русски, простыми действиями, с командами для копирования и ожидаемым результатом.

## Закрывать класс, а не случай

Решение владельца 2026-08-12 по итогам T-0118.

- **Замечание ревью — это пример, а не спецификация.** Закрывать нужно механизм,
  из-за которого пример стал возможен. Если правка закрывает ровно названный
  случай, следующий ревьюер найдёт соседний.
- **Перечисление имён или значений, которые задаёт не репозиторий, защитой не
  является.** Признак негодной защиты простой: спроси, кто решает, каким будет
  следующий элемент списка. Если внешняя система, провайдер или пользователь —
  список неполон по построению, и его неполнота не видна ни в одном зелёном
  прогоне. Allowlist собственных значений это правило не запрещает: там состав
  задаём мы.
- **Проверка должна ловить класс.** Тест на конкретное имя зеленеет ровно до
  следующего имени. Подкладывайте в проверку заведомо неизвестный элемент — так
  видно, работает механизм или совпадение.

Цена измерена: T-0118 прошла четыре круга независимого ревью, и каждый круг
находил новую утечку секретов в логи одного и того же прокси — OAuth2-код,
ключ управления через неканоническое имя заголовка, параметры OAuth1, наконец
заголовок вебхука, имя которого выбирает сам ученик. Каждый раз правка
закрывала названный случай и зеленила гейт. Помогла только смена принципа:
query и заголовки стали вырезаться целиком.

## Самостоятельность и отчётность агента

Решение владельца 2026-08-12.

- **Мелкие некритичные находки агент берёт в работу сам**, а не выносит на
  согласование. Замечание ревью, опечатка, неточная формулировка, устаревшая
  ссылка, недостающая проверка — чинятся сразу, в текущей или соседней задаче.
- **Владельцу выносится только то, что он один и может решить**: продуктовое
  решение, приоритет, деньги и планы, доступы, необратимое или боевое действие,
  расширение объёма задачи. Всё остальное — работа агента.
- **В спорном случае заводится соседняя задача, а не расширяется текущая.**
  Это правило по умолчанию: оно не требует согласования и не размывает scope.
- **Отчёт краткий и по делу.** Два рабочих формата:
  - сделано: что сделал, результат проверок, коммит;
  - нужно решение: в чём проблема, какие варианты, что требуется от владельца.
- **Стены текста не писать.** Подробности живут в evidence Projects Control и в
  сообщении коммита, а не в ответе. В ответе — вывод и следующий шаг.
- Незакрытое и невыполненное при этом называется прямо: краткость не повод
  умолчать о том, что не сделано.

## Ветки и выкатка

Решение владельца 2026-08-12.

- **Разработка идёт в ветке, но ветка остаётся локальной.** На GitHub уходит
  только `main`: работа коммитится в локальную ветку, вливается в `main`
  локально, пушится `main`. Ветки на `origin` не создаются и PR не открываются.
- **Причина.** Каждая ветка на GitHub создаёт превью-деплой Vercel, а план
  упирается в лимит веток — превью не собирается, и проверка на PR всегда
  красная. Удаление веток после мержа этого не сняло.
- **CI при этом не теряется:** `quality-gates` и `platform-quality` запускаются и
  на `push` в `main`, а не только на `pull_request`. Разница в моменте: гейты
  идут после попадания в `main`.
- **Поэтому релевантные проверки прогоняются локально до пуша** — как минимум
  `make quality`, плюс гейты, относящиеся к изменению. Толкать в `main`
  непроверенное нельзя: чинить придётся уже в `main`.
- **Выкатка выполняется только с `main` и только явным действием.** Мерж прод не
  обновляет: git-деплои выключены в `platform/vercel.json` (значение смотреть
  там — цитата здесь уже расходилась с конфигом). Порядок всегда один:
  разработали → мерж в `main` → выкатка. Команды — в
  [vercel foundation runbook](docs/vercel-foundation-runbook.md).
- **Локальная ветка после мержа удаляется** — она уже не нужна, а на `origin`
  её и не было.
- **Git-деплои Vercel отключены целиком** (`git.deploymentEnabled` в
  `platform/vercel.json`, T-0122): превью на PR блокировались лимитом веток на
  стороне Vercel, который
  пережил удаление веток в GitHub (доказано пробой при двух ветках на origin),
  а в рабочем процессе с локальными ветками git-превью и не используются.
  Проверки Vercel на PR теперь нет вовсе — её отсутствие норма, а не проблема.
  Ручное превью по-прежнему доступно: `vercel` без `--prod` из корня репо.
  Сигнал о коде дают GitHub Actions `quality` и `platform`. У `platform` есть
  path-фильтр, и он **шире** `platform/**` — состав смотреть в
  `.github/workflows/platform-quality.yml`, здесь он намеренно не переписан:
  копия разошлась бы с конфигом молча. Если изменение не задевает ни один путь
  фильтра, проверка не запускается вовсе — её отсутствие не признак проблемы и
  ждать её не нужно.
- **Выкатка нужна, когда менялся код платформы** — то, что попадает в её
  рантайм: всё под `platform/`, кроме markdown-файлов вроде `platform/AGENTS.md`
  и `platform/README.md`. Документация репозитория, корневой `AGENTS.md` и файлы
  starter kit в рантайм не входят и выкатки не требуют: они уезжают на VPS
  релизным артефактом, а не деплоем.
- **Выкатка считается состоявшейся только по факту**: коммит production-деплоя
  обязан содержать последнее изменение кода платформы, попавшее в `main`.
  Отсутствие ошибок при запуске команды доказательством не является.

Цена нарушения измерена: с 2026-08-09 по 2026-08-12 прод простоял на коммите,
закреплявшем релиз `v0.1.4`, чей артефакт не резолвится `docker compose`. Всё это
время провижининг нового ученического сервера был сломан, а четыре исправления
закреплённого релиза лежали в репозитории невыкаченными.

## Definition of Done задачи

Задача завершена только когда выполнены её acceptance criteria, обновлён documentation outcome, пройдены релевантные проверки, evidence привязан в Projects Control и независимое review одобрило результат.
