# Changelog

Все существенные изменения n8n Entrepreneur Starter Kit фиксируются здесь.
Формат основан на Keep a Changelog; версии соответствуют публичным GitHub
Releases.

## [Unreleased]

### Release gate

- Полный MVP claim остаётся `NO-GO`, пока новый независимый новичок не завершит
  чистый путь до editor за 15–30 минут без устных подсказок.
- Реальные Generic/Yandex/GigaChat, Telegram, email и CRM provider smokes
  остаются external-unverified, если для конкретного provider не указано иное.

## [0.1.13] - 2026-08-12

Ответные заголовки вырезаются из лога managed Caddy целиком, как и запросные
(T-0127): их имена задают n8n и сам ученик через Respond to Webhook, поэтому
прежний точечный фильтр только по `Location` был неполон по построению.
Диагностический размен записан в `docs/security.md`; живой прогон гейта получил
фиктивный upstream и подкладывает секреты на обеих сторонах.

Первый релиз с путём обновления кода уже развёрнутых хостов (T-0130):
`N8N_BOOTSTRAP_UPDATE_CODE=1 sh install.sh` обновляет код существующей
установки, сохраняя данные, secrets и volumes — см.
`docs/starter-kit-code-update.md`.

## [0.1.12] - 2026-08-12

Поведение managed-профиля не менялось. Релиз перевыпущен потому, что комментарий
профиля входит в закреплённый артефакт, а он содержал неверную опись того, что
остаётся в логе, и умалчивал про карту `resp_headers` — единственное место, где
утечка остаётся открытой.

Состав записи теперь описан в одном месте, `docs/security.md`; конфиг и этот
файл на него ссылаются. Копия расходилась с фактом дважды.

## [0.1.11] - 2026-08-12

Четвёртая утечка того же класса, поэтому принцип вырезания распространён на
заголовки запроса.

### Исправлено

- **Заголовки запроса удаляются целиком, а не по списку имён.** Независимое
  ревью нашло, что секрет в произвольном заголовке печатается в обоих логгерах.
  Канал не гипотетический: вебхуки n8n используют `headerAuth`, где имя
  заголовка выбирает сам ученик, а значение и есть секрет вебхука — четыре
  workflow репозитория так и настроены. Список из трёх имён закрыть этот канал
  не мог в принципе;
- гейт требует удаления всей карты `request>headers` у каждого логгера, а живой
  прогон подкладывает секреты в заведомо неизвестные имена заголовков;
- из профиля убраны два комментария, не соответствовавших коду после перехода на
  вырезание: про намеренное сохранение `state` и про блочную форму фильтра.

### Цена

В логе больше нет ни одного заголовка запроса, включая `User-Agent`. Полный
состав того, что остаётся, — в `docs/security.md`: пересказ здесь уже один раз
разошёлся с фактом.

### Осталось открытым

Произвольные ответные заголовки по-прежнему не фильтруются — закрыт только
`Location`. Вынесено в отдельную задачу: удалять все поля ответа нельзя не
думая, это оставит без диагностики проксирования.

## [0.1.10] - 2026-08-12

Третий круг по одной и той же теме, поэтому меняется не список, а принцип.

### Исправлено

- **Query вырезается целиком, а не редактируется по именам параметров.**
  Независимое ревью нашло очередную утечку: `/rest/oauth1-credential/callback`
  несёт `oauth_token` и `oauth_verifier`, которых не было ни в одном списке.
  Маршрут проверен в закреплённом образе n8n `2.29.10`. Там же выяснилось, что
  сверка имён чувствительна к регистру — `?Token=` не совпадал с `token`, — и
  что мимо списка проходят `access_token`, `api_key`, `password` и прочие. Набор
  секретных имён задают n8n и внешние провайдеры, поэтому перечислить их заранее
  нельзя. Теперь в логе остаётся только путь;
- `Location` фильтруется наравне с `Referer`: редирект от n8n может нести код в
  query;
- гейт проверяет отсутствие `servers { log_credentials }` — эта опция возвращает
  `Authorization` в лог целиком и не видна ни в одном фильтре полей;
- живой прогон гейта расширен до тринадцати подложенных секретов, включая
  OAuth1, другой регистр и имена вне любых списков.

### Цена

Несекретные параметры вроде `state` тоже перестают попадать в лог. Путь, метод,
код ответа и время остаются.

## [0.1.9] - 2026-08-12

Найдено независимым ревью T-0118 и подтверждено живым запросом.

- **Ключ управления n8n печатался в логи.** `request>headers>X-N8N-API-KEY delete`
  был no-op: имя заголовка сравнивается с канонической формой Go, поэтому
  написанное as-is не совпадает никогда. `Cookie` и `X-Neurokurs-Management`
  удалялись, потому что их написание уже каноническое. Правильная форма —
  `X-N8n-Api-Key`;
- **токен приглашения утекал через `Referer`.** При нашей `Referrer-Policy`
  браузер шлёт полный URL предыдущей страницы на same-origin подзапросы, а n8n —
  SPA, поэтому `/signup?token=...` приезжал в заголовке следующего запроса.
  Теперь `Referer` фильтруется тем же `query`;
- **гейт проверял объявленные поля, а не эффект,** и потому пропускал обе
  утечки: директива написана, эффекта нет. Добавлен живой прогон с шестью
  подложенными секретами, ни один из них не должен попасть в лог. Прогон
  дополнительно проверяет, что лог виден, иначе «ноль секретов» ничего не значит.

## [0.1.8] - 2026-08-12

Закрывает утечку секрета в логи managed Caddy и слабость гейта, который её
сторожил.

### Исправлено

- **OAuth2-код n8n больше не печатается в логах.** Через общий `handle` идёт
  `/rest/oauth2-credential/callback?code=...&state=...`; параметр `code`
  обменивается на токен доступа к внешнему сервису ученика и до этой версии
  уходил в оба логгера целиком — воспроизведено живым запросом. Соседний `state`
  оставлен намеренно: это CSRF-nonce, без `code` он бесполезен, а по нему
  сопоставляют запрос и ответ при разборе неудачной привязки credential;
- **гейт больше не обходится добавлением логгера.** Прежняя проверка считала
  логгеры *с* редакцией и требовала ровно двух, поэтому третий —
  `log extra { output stdout }` — оставлял её зелёной при живом логгере без
  редакции.
  Теперь редакция требуется у **каждого** логгера из `.logging.logs`, вместе с
  удалением `Cookie`, `X-N8N-API-KEY` и `X-Neurokurs-Management`;
- две `grep`-проверки на удаление заголовков убраны как более слабые: они
  смотрели текст конфига и проходили ровно в том сценарии, который надо было
  поймать.

Закреплённые образы не менялись: n8n `2.29.10`, PostgreSQL `17.10-bookworm`,
Caddy `2.11.4-alpine`.

## [0.1.7] - 2026-08-11

Поведение managed-профиля не менялось. Релиз перевыпущен потому, что комментарий
профиля входит в закреплённый артефакт, а он содержал ложное утверждение
«проверено живым запросом» — тот же класс дефекта, который чинила предыдущая
версия.

### Исправлено

Утверждалось, что при пустой `SITE_VERIFICATION_FILE` вход в n8n начинает
отдавать `404`. Фактически `GET /` отдаёт `200` с телом
`google-site-verification: ` вместо редактора n8n, а `robots.txt` вырождается в
`Disallow: /` плюс `Allow: /` — правило равной длины снимает запрет обхода, то
есть заодно отменяется мера `0.1.5` против индексации. Второе следствие не было
описано вообще.

Отказ тихий: код ответа остаётся `200`. Поэтому применение профиля проверяется
по **телу** корня — признак поломки, строка `google-site-verification:` в ответе
на `/`, — а не по коду ответа. Проверка вида «корень не отдаёт `404`» зелёная в
обоих состояниях и бесполезна.

`.env.platform.example` больше не пугает пустым значением: в managed-профиле его
нейтрализует подстановка `:-`.

## [0.1.6] - 2026-08-11

Релиз выпущен потому, что общий managed-профиль нёс личный файл подтверждения
права собственности в поисковой консоли. Файл привязан к **аккаунту** владельца,
а не к сайту, а `config/Caddyfile.platform` едет в публичном релизном артефакте
и разворачивается на произвольных хостах: любая посторонняя установка starter
kit начинала отдавать чужое доказательство владения. Практическая экспозиция
удерживалась только guard по хосту в коде платформы, который распространяется
отдельно от конфига.

### Исправлено

- имя файла подтверждения приходит из `SITE_VERIFICATION_FILE` конкретного
  хоста, тело ответа выводится из него же; без переменной endpoint остаётся на
  заведомо инертном пути (T-0123);
- гейт `compose-config` привязан к **пути** обработчика, а не только к телу
  ответа: переименование `handle /robots.txt` оставляло проверки зелёными, пока
  `/robots.txt` снова уходил в n8n и отдавал SPA-оболочку с кодом `200`;
- исправлено неверное утверждение в `config/Caddyfile.platform` и
  `docs/security.md` о том, что `robots.txt` обязан стоять до общего `handle`:
  Caddy сортирует `handle` по специфичности матчера, а не по месту в файле;
- `.env.platform.example` больше не предлагает снятую `PLATFORM_GATE_ORIGIN`
  (ADR-0016) и описывает новую переменную.

### Ловушка конфигурации

Пустое значение `SITE_VERIFICATION_FILE` опаснее отсутствующего: подстановка
`{$VAR:default}` внутри Caddyfile читает `default` только когда переменная не
определена вовсе, а определённое пустое значение оставляет матчер `/` и
перехватывает корень сайта — вход в n8n начинает отдавать `404`. Отсюда `:-` в
`docker-compose.platform.yml` и отдельная проверка в гейте.

Закреплённые образы не менялись: n8n `2.29.10`, PostgreSQL `17.10-bookworm`,
Caddy `2.11.4-alpine`.

## [0.1.5] - 2026-08-09

Релиз выпущен из-за того, что закреплённый `v0.1.4` ломал новую установку
управляемой среды. Он был собран за день до снятия gateway и нёс
`docker-compose.platform.yml` с обязательной переменной `PLATFORM_GATE_ORIGIN`,
которую после ADR-0016 больше никто не задаёт: `docker compose` отказывался
резолвить конфигурацию ещё до запуска контейнеров.

Расхождение не было видно в `git diff`, потому что конфигурация едет внутри
`install.sh` встроенным архивом.

### Изменено

- managed Caddy profile без `forward_auth` и `/__neurokurs/exchange`: ученик
  входит в n8n по собственному аккаунту (ADR-0016);
- одноразовый токен приглашения редактируется в access- и error-логах Caddy;
- добавлены собственный `robots.txt` с `Disallow: /` и заголовок
  `X-Robots-Tag: noindex, nofollow`;
- добавлен файл подтверждения владения Google Search Console, переживающий
  переустановку среды.

Закреплённые образы не менялись: n8n `2.29.10`, PostgreSQL `17.10-bookworm`,
Caddy `2.11.4-alpine`.

## [0.1.4] - 2026-08-04

Первый релиз из консолидированного репозитория
`marcusaure1ius/alfa-ai-course`. Канал установки переехал туда же.

### Added

- Обход Docker Hub `429` через официальный proxy Timeweb в основной ветке.
- Технический E2E публичной установки на чистом VPS как отдельное evidence.

### Changed

- Payload one-command installer больше не содержит исходники Course Control
  Plane: границы distributable заданы в `.gitattributes` и закреплены тестом.
- Провижининг платформы указывает на новый installer; версия bootstrap-профиля
  поднята до `starter-kit-v0.1.5`, поэтому сохранённый план со старым
  установщиком отвергается как `INVALID_INSTALL_PLAN`.
- Разведена коллизия трёх ADR-0012.

### Прочее

Релизы `0.1.2` и `0.1.3` публиковались из релизной ветки и отдельных записей
здесь не получили. Они остаются доступны в заархивированном репозитории
`n8n-entrepreneur-starter-kit` как путь отката.

## [0.1.1] - 2026-07-31

### Added

- Пошаговый SSH onboarding с нуля для macOS/Linux и Windows 10/11, включая
  создание ключа и путь через provider web-console.
- Timeweb-specific allowlisted Docker registry proxy с bounded retry и
  сохранением exact image tags.
- Структурированный novice route с явными действиями, вставкой команд и
  ожидаемыми результатами.

### Changed

- Clean install сразу устанавливает n8n `2.29.10`; пара `2.29.9 → 2.29.10`
  описана только как отдельный lifecycle update/rollback rehearsal.
- Stable installer пересобран из commit
  `68063340c8113d98586f71704c30adc6d1f0eb3a`.

### Verified

- Public asset checksum и embedded payload verification.
- Реальный Timeweb install через proxy до HTTPS owner setup и editor.
- Novice trial остаётся FAIL как полный 15–30-минутный path; targeted recovery
  после исправлений прошёл.
